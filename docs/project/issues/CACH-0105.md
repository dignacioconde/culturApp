# CACH-0105 — Memoria v2 compacta y medible

## Objetivo

Reducir el coste de contexto de `.memory/` y convertir su recuperación en un flujo determinista, selectivo y verificable sin servicios externos.

## Alcance

Incluido:

- Compactar memoria durable y retirar histórico o referencias redundantes.
- Usar `.memory/MEMORY.md` como índice único de routing.
- Añadir comandos de selección, validación estructural y benchmark.
- Alinear las skills y la política de contexto.
- Bloquear errores estructurales en CI y mantener el benchmark como advisory.

Fuera de alcance:

- Código funcional de la app, Supabase, datos de usuario o producción.
- Embeddings, base vectorial, judge LLM o memoria de sesión persistida.

## Criterios de aceptacion

- [x] AC1: La memoria queda reducida al menos un 50% sin perder las reglas durables activas.
- [x] AC2: `memory:route` selecciona un máximo de tres archivos y usa `core.md` como fallback.
- [x] AC3: `memory:check` bloquea rutas, enlaces, orphans, stubs o claves volátiles inválidas.
- [x] AC4: El benchmark alcanza 100% de precisión y cobertura dentro de 2.000 tokens.
- [x] AC5: CI bloquea por estructura y ejecuta el benchmark como advisory.
- [x] AC6: Skills y documentación usan una sola tabla de rutas y separan memoria durable de estado efímero.

## Plan tecnico

Centralizar parsing, routing, métricas y validación en un módulo Node reutilizable. Exponer tres scripts pnpm sin dependencias nuevas y usar el estimador de tokens existente. Mantener Markdown como formato humano y Git como histórico.

## Escenarios SDD

- Cuando una tarea coincide con un área, entonces se cargan solo sus destinos relevantes dentro del presupuesto.
- Cuando cruza áreas, entonces se combinan destinos sin duplicados y con máximo tres archivos.
- Cuando no hay coincidencias, entonces solo se recupera `core.md`.
- Cuando existe una ruta rota, orphan, clave volátil duplicada o stub activo, entonces `memory:check` falla.
- Cuando el benchmark incumple calidad, entonces informa en CI y falla únicamente con `--strict`.

## Contrato tecnico

- `.memory/MEMORY.md`: tabla `Área | Señales | Destinos | Política`.
- `pnpm memory:route -- "descripción de tarea" [--json]`: selección y coste estimado.
- `pnpm memory:check [-- --json]`: gate estructural.
- `pnpm memory:benchmark [-- --json] [--strict]`: evaluación determinista.
- CI `app`: check bloqueante y benchmark advisory.

## Riesgos y rollback

Riesgo principal: una señal insuficiente puede omitir memoria relevante. Mitigación: fixtures representativos, fallback y tabla editable. Rollback: revertir scripts, comandos e índice sin tocar runtime ni datos.

## Validacion

- AC1 -> recuento Git antes/después.
- AC2, AC4 -> `pnpm memory:benchmark -- --strict`.
- AC3 -> `pnpm memory:check` y fixtures de ciclo de vida.
- AC5 -> `pnpm verify:ci` y revisión del workflow.
- AC6 -> `pnpm context:check`, `pnpm verify:skills` y `git diff --check`.

## Resultado

Memoria reducida de 8.880 a 3.096 palabras (65%). El benchmark pasa 12/12 escenarios con precisión y cobertura del 100%, máximo de dos archivos, 1.526 tokens y carga media del 18,9% frente a abrir toda la memoria activa.
