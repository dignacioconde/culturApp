# CACH-0101 — Versionar schema y RLS de gastos repercutibles

## Objetivo

Añadir persistencia segura y aditiva para marcar gastos repercutibles y, cuando aplique, enlazarlos con ingresos del mismo usuario/trabajo.

## Alcance

- Crear migracion versionada segun el contrato de `CACH-0100`.
- Añadir campos opcionales a `expenses` para distinguir gasto interno/repercutible y enlace opcional con `incomes`.
- Mantener intactos ingresos, gastos, contratantes, `project_id`, `event_id` y datos legacy.
- Asegurar que RLS y constraints impiden cruces de usuario.
- Actualizar README/TECHDOC si el schema canonico cambia.

Queda fuera: UI final, helpers de calculo, facturas, pagos, IVA y cambios del dashboard.

## Criterios de aceptacion

- [x] AC1: Existe migracion local versionada, aditiva y sin borrado de datos existentes.
- [x] AC2: Los nuevos campos de `expenses` son opcionales y tienen defaults compatibles con los gastos actuales.
- [x] AC3: El enlace gasto -> ingreso no permite relacionar filas de usuarios distintos.
- [x] AC4: La constraint actual `project_id is not null or event_id is not null` se mantiene.
- [x] AC5: Hay SQL read-only documentado para verificar columnas, constraints, foreign keys y policies en remoto.

## Plan tecnico

Partir de la decision de `CACH-0100`. Si se usa FK compuesta por usuario, preparar el indice/constraint necesario en `incomes` antes de referenciarla desde `expenses`. No ejecutar migraciones remotas sin confirmacion humana.

## Escenarios SDD

- Cuando se aplica la migracion sobre una base existente, entonces los gastos antiguos siguen siendo validos y no quedan marcados como repercutibles por error.
- Cuando un gasto intenta enlazarse a un ingreso de otro usuario, entonces la base de datos lo rechaza.
- Cuando un gasto mantiene solo `project_id` o solo `event_id`, entonces sigue cumpliendo el contrato de vinculacion actual.

## Contrato tecnico

Contratos afectados:

- `supabase/migrations/**`
- `README.md` schema inicial si procede.
- `TECHDOC.md` inventario de tablas/estado si procede.
- Futuro consumo por `useExpenses`, portabilidad y detalles financieros.

## Riesgos y rollback

Riesgo principal: una FK o constraint demasiado estricta que bloquee gastos existentes. Rollback esperado: migracion inversa o nueva migracion que retire campos/constraints aditivos sin tocar filas core.

## Resultado

Implementada migracion local `supabase/migrations/20260520120000_reimbursable_expenses.sql`:

- Añade `expenses.expense_kind text not null default 'internal'`.
- Añade `expenses.reimbursed_by_income_id uuid references public.incomes(id) on delete set null`.
- Mantiene `chk_expense_link`.
- Añade checks de tipo y enlace.
- Recrea policies de `incomes` y `expenses` con `with check (auth.uid() = user_id)`.
- Añade trigger `expenses_validate_reimbursement_link` para impedir cruces de usuario y de alcance `project_id`/`event_id`.

SQL read-only remoto para verificar antes de cerrar produccion:

```sql
select column_name, data_type, is_nullable, column_default
from information_schema.columns
where table_schema = 'public'
  and table_name = 'expenses'
  and column_name in ('expense_kind', 'reimbursed_by_income_id');

select conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid = 'public.expenses'::regclass
  and conname in (
    'chk_expense_link',
    'expenses_expense_kind_check',
    'expenses_reimbursement_link_check'
  );

select tgname
from pg_trigger
where tgrelid = 'public.expenses'::regclass
  and not tgisinternal
  and tgname = 'expenses_validate_reimbursement_link';

select tablename, policyname, qual, with_check
from pg_policies
where schemaname = 'public'
  and tablename in ('incomes', 'expenses')
order by tablename, policyname;
```
