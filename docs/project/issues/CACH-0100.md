# CACH-0100 — Definir contrato de liquidacion neta minima

## Objetivo

Cerrar el contrato de producto y datos para una liquidacion neta minima que pueda implementarse sin convertir Cachés en sistema de facturacion.

## Alcance

Incluido:

- Definir que significa gasto interno, gasto repercutible y gasto enlazado a un ingreso.
- Definir la formula minima de liquidacion neta para detalle de proyecto y detalle de evento.
- Confirmar que el dashboard mensual sigue centrado en cobros/ingresos y no adopta gastos ni neto como KPI principal.
- Definir los campos aditivos que necesita `expenses` y las reglas de coherencia con `incomes`.
- Decidir si hace falta ADR antes de implementar schema o si basta con documentar el contrato en esta issue y en la release.

Fuera de alcance:

- Facturas emitidas, numeracion fiscal, IVA, PDF, CRM, pagos, conciliacion bancaria y colaboracion multiusuario.

## Criterios de aceptacion

- [x] AC1: El contrato distingue gasto interno, gasto repercutible y gasto enlazado a un ingreso con nombres usables en UI.
- [x] AC2: La formula de liquidacion neta queda definida para proyecto y evento sin modificar `cobro bruto/hora`.
- [x] AC3: El contrato especifica que el dashboard mensual conserva `Caja del mes` y `Trabajos` como vista de cobros/ingresos.
- [x] AC4: El contrato de datos indica campos, nulabilidad, RLS y coherencia usuario/proyecto/evento esperada para el slice de schema.
- [x] AC5: El scope excluido queda suficientemente explicito para no derivar hacia facturacion completa.

## Plan tecnico

Revisar `CACH-B0004`, beta 19, hooks financieros actuales y memoria de dashboard. El resultado debe dejar un contrato breve para `CACH-0101`, `CACH-0102` y `CACH-0103`, incluyendo nombres de campos propuestos o criterios para elegirlos.

## Escenarios SDD

- Cuando un gasto es interno, entonces reduce el neto operativo del trabajo pero no aparece como importe repercutido al cliente.
- Cuando un gasto es repercutible y se enlaza a un ingreso del mismo usuario y trabajo, entonces la liquidacion muestra ese gasto como cubierto por ese ingreso sin duplicar ingresos.
- Cuando un proyecto tiene eventos hijos, entonces el resumen de proyecto agrega gastos/ingresos directos y de eventos igual que los detalles actuales, salvo la regla especial de `cobro bruto/hora`.
- Cuando el usuario abre el dashboard, entonces los KPIs principales siguen sin usar gastos ni neto.

## Contrato tecnico

Contrato cerrado:

- Gasto interno: `expense_kind = internal`; reduce el neto operativo y no aparece como gasto repercutido.
- Gasto repercutible: `expense_kind = reimbursable`; se separa como gasto que puede estar cubierto por un ingreso, sin crear ingresos duplicados.
- Enlace gasto -> ingreso: `expenses.reimbursed_by_income_id` opcional y solo valido para gastos repercutibles.
- Formula minima de detalle: `neto_operativo = ingresos_cobrados - IRPF_sobre_cobrados - gastos_internos - gastos_repercutibles`.
- Proyecto: agrega ingresos/gastos directos y de eventos hijos igual que el detalle actual; evento: usa solo sus registros.
- `cobro bruto/hora`: sigue usando solo ingresos cobrados con `event_id` y horas de eventos con `end_datetime`.
- Dashboard mensual: conserva `Caja del mes` y `Trabajos` como vista de cobros/ingresos; no adopta gastos ni neto.
- RLS/coherencia: `expenses.user_id` e `incomes.user_id` son directos; el enlace debe compartir usuario y el mismo alcance `project_id`/`event_id`.
- Fechas: mantener `expense_date`, `expected_date` y `paid_date` con semantica actual.

## Riesgos y rollback

Riesgo principal: que "liquidacion neta" se confunda con beneficio contable o facturacion legal. Rollback: documentar que el primer corte es solo resumen operativo y mantener schema aditivo que pueda ignorarse si se desactiva la UI.
